# Пер-профильный пайплайн вакансий, статистика и цикл

Дата: 2026-07-24
Статус: реализовано (питон-часть — коммиты work-autopilot до `218684f`; см. также
«Инцидент 2026-07-24» ниже)

## Проблема и цель

Сейчас автопилот работает на **общем пуле** вакансий: скан один раз кладёт union всех
поисков в `queue`, а профили лишь берут из него релевантное своему резюме. Ротация в
цикле идёт по батчу откликов, чат — отдельным кругом, богатой статистики нет.

Цель — сделать пайплайн **пер-профильным** и наблюдаемым:

- у каждого профиля свой пул вакансий; поиск (скан) идёт под аккаунтом профиля по его
  собственным поисковым URL;
- при выборе профиля виджет показывает только его группы и его статистику;
- богатая статистика профиля: новые по группам (пока не обогащено), отклики, ответы в
  чате, протухшие, 403, капчи, заполненные гугл-формы — за текущий ход и за всё время;
- ранжирование (свежесть × релевантность к резюме) естественно становится пер-профильным;
- цикл ротирует профили по правилу «27 откликов → разобрать чат → следующий».

Единственный источник правды по состоянию — `data/autopilot.db`. Файлов состояния на
диске (`scan.json`, `stats-<profile>.json`) больше нет.

## Ключевые решения (из брейншторма)

1. **Полный пер-профильный скан.** Каждый профиль сканит под своим аккаунтом браузера
   только свои группы. Пул тегируется профилем; одна вакансия под двумя профилями —
   две независимые строки (свой вектор, свой дедуп).
2. **Свои URL у профиля.** Поисковые URL переезжают в оверлей профиля
   (`config/profiles/<name>.yaml → site.listings_urls`). Глобальный union в
   `config.yaml` убирается.
3. **Статистика «за текущий ход + всё время».** «Ход» = текущий заход профиля в цикле.
4. **Правило хода профиля:** отклики до **27**, затем чат — разобрать все непрочитанные
   с крышками **40 ответов** и **30 минут в чате**; потом эстафета следующему профилю.
5. **Порядок внутри хода:** сначала все 27 откликов, затем чат до крышек.
6. **Скан — раз в сутки на профиль.** Первый ход профиля за день делает скан+обогащение;
   последующие ходы того же дня работают по уже набранному пулу.
7. **Всё в БД, лёгкий мост.** Виджет читает статистику через новую подкоманду
   `autopilot summary`, печатающую JSON в stdout (только SQL, без импорта torch). Метку
   старта хода виджет держит в RAM и передаёт как `--since`.

## Модель цикла

```
Раз в сутки на первый ход профиля за день:
  scan(профиль, его группы)   # под аккаунтом профиля
  enrich(пул профиля)

Ход профиля (крутится весь день по кругу):
  apply-проходы   до 27 успешных откликов ИЛИ пул профиля исчерпан
  chat-проходы    разобрать непрочитанные; крышки: 40 ответов ИЛИ 30 минут в чате
  → следующий eligible-профиль
Круг не даёт прогресса / все в дневном лимите → цикл спит до следующего дня.
```

- Ротация целиком на стороне виджета (`src/main.rs`), как сейчас. Триггер меняется с
  «батч 27 / дневной лимит» на правило хода (см. ниже).
- `apply` и `chat` остаются отдельными фазами/процессами (одно окно на профиль); виджет
  чередует их в рамках хода: сначала добирает 27 откликов, потом чат до крышек.
- Пул исчерпан раньше 27 → apply-фаза завершается сама, ход переходит к чат-части (уже
  существующий механизм `applies_exhausted`).

### Константы (в одном месте, `main.rs`)

- `APPLY_TARGET = 27` — цель откликов за ход (заменяет `APPLY_BATCH_SIZE`).
- `CHAT_REPLY_CAP = 40` — крышка ответов в чате за ход.
- `CHAT_TIME_CAP = 30 min` — крышка времени чат-фазы за ход.

### Правило завершения хода (чистая функция, тестируемая)

Ход профиля завершён, когда:
- `applied_in_turn >= APPLY_TARGET` **или** пул исчерпан (apply-часть закрыта), И
- чат-часть закрыта: все непрочитанные разобраны **или** `replied_in_turn >= CHAT_REPLY_CAP`
  **или** время чат-фазы `>= CHAT_TIME_CAP`.

Сигналы для виджета:
- `applied_in_turn`, `replied_in_turn` — из `summary` (`applied.turn`, `replies.turn`,
  `since` = метка старта хода в RAM).
- «Все непрочитанные разобраны» — пустой чат-проход: `ChatResponder.run_once`
  возвращает число обработанных диалогов, и при 0 за целый проход `run --chat`
  завершает процесс. Виджет на выходе чат-процесса в цикле ротирует ход
  (`rotate_to_next_profile`), не дожидаясь 30-минутной крышки — она остаётся
  предохранителем. (Реализовано 25.07: до этого сигнал был захардкожен `false`,
  и пустой чат пережидал всю крышку.)
- Время чат-фазы — таймер в RAM виджета, стартует при входе в чат-часть хода.

## Модель данных (SQLite)

### queue — пер-профильный пул

```sql
CREATE TABLE queue(
  profile      TEXT NOT NULL,
  vacancy_id   TEXT NOT NULL,
  group_name   TEXT NOT NULL,
  title        TEXT,
  url          TEXT,
  body         TEXT,
  embedding    BLOB,
  published_at TEXT,
  employer     TEXT,
  enriched     INTEGER NOT NULL DEFAULT 0,
  unavailable  INTEGER NOT NULL DEFAULT 0,
  found_at     TEXT DEFAULT (datetime('now','localtime')),
  PRIMARY KEY (profile, vacancy_id)
);
```

- Все методы пула получают параметр `profile`: `enqueue`, `candidates_for`,
  `candidates_to_enrich`, `queue_counts`, `unenriched_count`, `mark_unavailable`,
  `enrich_row`, и схлопывание клонов (`_collapse_*`, `_clone_*`).
- Схлопывание клонов и дедуп — **в пределах профиля**.
- Миграция: если в `queue` нет колонки `profile` — пересоздать таблицу с составным PK,
  существующие строки перенести как `profile='fullstack'` (исторический аккаунт по
  умолчанию), по образцу уже сделанной миграции `applications`.

### events — лог событий для счётчиков

```sql
CREATE TABLE events(
  profile TEXT NOT NULL,
  kind    TEXT NOT NULL,   -- applied | reply | captcha | form_filled | http_403 | expired
  ts      TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS events_profile_ts ON events(profile, ts);
```

Точки инкремента (добавляем `store.log_event(profile, kind)` в существующий код, не меняя
его логику):

- `applied` — успешный отклик (listings, рядом с `record_application(status='applied')`).
- `reply` — успешный ответ в чате (chat, при отправке ответа работодателю).
- `captcha` — колбэк `on_captcha` (адаптер/enrich).
- `form_filled` — успешная отправка гугл-формы (`chat_forms`).
- `http_403` — `BrowserFetcher` поймал 403.
- `expired` — вызов `mark_unavailable` (снятая/архивная).
- `enriched` — успешное обогащение вакансии (`PoolEnricher`, рядом с `enrich_row`); даёт
  разрез «обогащено сегодня» без отдельной колонки-таймстампа.

`applied`/`reply` дублируют выводимое из `applications`/`chats`, но единый лог даёт ровный
разрез «за ход (since)» без спец-логики на каждый счётчик.

### profile_meta — снимок топ-N для лёгкого summary

```sql
CREATE TABLE profile_meta(
  profile  TEXT PRIMARY KEY,
  top_json TEXT,          -- JSON-массив топ-N заголовков ранжирования
  updated_at TEXT DEFAULT (datetime('now','localtime'))
);
```

Тяжёлая apply-фаза (`ListingHunter`, где embedder уже загружен) после ранжирования
пишет топ-N заголовков сюда. `summary` только читает `top_json` — без encode/torch.

### Дата последнего скана профиля

Выводим из `SELECT MAX(found_at) FROM queue WHERE profile = ?` (отдельная таблица не
нужна). Виджет по дате решает, нужен ли дневной скан.

## Конфиг

- Поиски переезжают в оверлеи профилей:

```yaml
# config/profiles/back.yaml
site:
  listings_urls:
    - {name: "Backend Go",       url: "https://hh.ru/search/vacancy?text=Backend+Go&..."}
    - {name: "Backend Python",   url: "https://hh.ru/search/vacancy?text=Backend+Python&..."}
    - {name: "Node.js разработчик", url: "https://hh.ru/...text=Node.js..."}
    - {name: "Rust разработчик",  url: "https://hh.ru/...text=Rust..."}
```

- fullstack получает явный оверлей `config/profiles/fullstack.yaml` с его текущими
  fullstack/frontend/LLM-поисками (сейчас они в базовом `config.yaml`).
- Базовый `config.yaml` держит только общее: промпты, `listings_filter`, селекторы,
  дефолтный `listings_url`-fallback. Глобальный `listings_urls`-union удаляется.
- Поле `groups` (allow-list имён) больше не источник для скана — группы профиля = имена
  его `listings_urls`. `SiteConfig.groups()` работает как есть, источник — пер-профильный
  после `_deep_merge` оверлея.
- Для **откликов** группы профиля = `bundle.groups` (явный allow-list, если задан), иначе
  имена его `listings_urls`. Ранжирование (`_rank_candidates`) отбрасывает строки пула
  с чужим `group_name` — строки чужих/переименованных групп, оставшиеся в БД от старых
  сканов, в отклик не попадают.
- **Стоп-слова по заголовку** (`listings_filter.exclude_title_keywords`, 25.07):
  junior/QA/стажёр лексически близки к резюме и эмбеддингом не режутся (Junior Full
  Stack — 0.617, QA fullstack — 0.628 при пороге 0.55); заголовок режет их точно, а
  сеньорская вакансия с «менторить джунов» в теле не страдает. Общий список — в базовом
  `config.yaml`; оверлей профиля ЗАМЕНЯЕТ его целиком (повторять общие слова!) и задаёт
  профильный уклон: fullstack исключает чисто-бекендерские заголовки (backend/бэкенд —
  для них профиль back), back исключает ML/LLM (для них профиль llm). Порог
  `MIN_SIMILARITY=0.55` остаётся страховкой от смыслового мусора снизу (<0.50 —
  бизнес-ассистенты, аналитики). Калибровка по пулу fullstack 25.07: 270 обогащённых →
  71 срезано стоп-словами, 140 ниже порога, 59 к отклику (цель 27/день).
  Тесты: `tests/test_rank_title_stopwords.py`.

## Скан и обогащение

- `run_scan`/`run_enrich` уже принимают `settings.profile_name` и оверлей `bundle`
  (запускаются с `--profile`). Меняется: методы Store вызываются с `profile`, работают со
  строками пула этого профиля.
- **Отработанные не обогащаются.** «Отработанность» помечается записью в `applications`
  (нет флага в строке `queue`). Enrich-очередь (`candidates_to_enrich`) и счётчики
  необогащённых (`unenriched_count`, `new_by_group`) используют тот же предикат, что и
  ранжирование: `enriched=0 AND unavailable=0 AND NOT EXISTS(applications по profile+vid)`
  — общий `Store._UNENRICHED_WHERE`. Иначе обогащение зря открывало бы в браузере уже
  отработанную вакансию, а кнопка «✨ Дообогатить (N)» показывала бы неотрабатываемый
  остаток (и цикл enrich выдавал бы ложное «похоже на блокировку»).
- Дневной гейт скана — в виджете: перед первым ходом профиля за день сверяет
  `last_scan_date` (из `summary`) с сегодняшней датой; если старее — запускает скан.
  Ручная кнопка скана — принудительно, как сейчас.

## Мост «виджет ↔ питон»: подкоманда summary

- `autopilot summary --profile <name> --since <iso>` → только SQL к Store, печатает JSON
  в stdout. **Не импортирует** Embedder/torch (отдельный лёгкий путь в `__main__`).
- JSON содержит:
  - `applied`: `{turn, total}` (turn = события `applied` с `ts >= since`);
  - `replies`: `{turn, total}`;
  - `captcha`/`forms`/`http_403`/`expired`: `{turn, total}`;
  - `groups`: `[{name, new}]` — новые (`enriched=0 AND unavailable=0`) по группам профиля;
  - `unenriched`: остаток необогащённых профиля;
  - `pool_total`: вся база вакансий профиля (`COUNT(*)` пула, включая обогащённые/снятые);
  - `found_today`: добавлено в пул сегодня (`date(found_at)=today`);
  - `enriched_today`: обогащено сегодня (событий `enriched` с `date(ts)=today`);
  - `last_scan_date`: `MAX(found_at)` профиля;
  - `top`: топ-N (5) заголовков ранжирования профиля (свежесть × релевантность),
    из **персистентного снимка** (см. ниже — ранжирование требует encode/torch, а
    `summary` лёгкий, поэтому снимок пишет тяжёлая apply-фаза, а `summary` его читает);
  - `applied_today`, `daily_limit` — для дневного лимита (как сейчас).
- Виджет захватывает stdout по таймеру (≈ раз в 2–3 с), кэширует, парсит через serde.
- Удаляем запись `scan.json`/`stats-<profile>.json` в питоне и подкоманду `scan-status`;
  чтение этих файлов в виджете (`pilot_scan.rs`, `pilot_stats.rs`) заменяем разбором
  stdout от `summary`.
- Метка старта хода — в RAM виджета (`Instant` + wall clock ISO), передаётся как `--since`.

## Отображение (виджет, блок «Автопилот», всегда развёрнуто)

Для активного профиля:

- Пул: `🗂 база {pool_total} · сегодня +{found_today} найдено · ✨ {enriched_today}
  обогащено` — размер базы, дневной приток и обогащение (кнопки групп показывают лишь
  остаток необогащённых, который тает по мере обогащения, поэтому база/приток вынесены
  отдельной строкой).
- Бар хода (только когда автопилот работает): четыре сегмента 🔎→✨→📨→💬 одной
  полосой. Ширина сегмента пропорциональна оставшемуся времени фазы (пройденные
  сжимаются в чипы), заливка — прогресс фазы, активная обведена, у скана прогресс
  неизвестен — пульс. Внутри сегмента иконка + минуты (если влезает). Эмпирические
  стоимости шагов (замер по логам 24.07): скан ~30с/группа, обогащение ~11с/вакансия,
  отклик ~40с; чат — остаток 30-минутной крышки. Кандидаты к отклику — из снимка
  `ranked` (profile_meta.ranked_count, пишется apply-фазой вместе с топ-5; пока снимка
  нет — остаток цели 27). Прогресс обогащения — от остатка на входе в фазу
  (`enrich_start` в RAM виджета). Чистые функции `turn_segments`/`seg_widths` +
  отрисовка `draw_turn_bar` в `main.rs`; тесты `turn_segments_states_and_secs`,
  `seg_widths_min_plus_proportional`.
- Отклики: `12/27 · план хода N` за ход · `340` всего. План хода = сколько откликов
  реально выйдет в цикле: цель 27, но не больше кандидатов после фильтров (снимок
  `ranked`); пока снимка нет — план не показывается.
- Ответы в чате: `3` за ход · `88` всего (+ таймер чат-фазы, когда идёт чат).
- Капча · Формы · 403 · Протухло — «за ход · всего».
- Новые по группам (пока не обогащено): `Backend Go 8 · Rust 2 · …`.
- Топ профиля: топ-5 заголовков ранжирования (то, по чему пойдут отклики).

## Границы (YAGNI)

- Без графиков/веб-дашборда — только текст в блоке.
- Механику откликов/чата/форм/капчи не трогаем — только добавляем `log_event` в
  существующих точках.
- Ранжирование (`_rank_candidates`, relevance + freshness) не переписываем.
- Legacy `data/browser-profile` fullstack не ломаем; fullstack получает явный оверлей.
- Виджет в БД не пишет (метка хода — в RAM).

## Тестирование

Питон (pytest):

- Миграция `queue` → составной PK `(profile, vacancy_id)`; старые строки → `fullstack`.
- Изоляция профилей: `enqueue`/`candidates_for`/`candidates_to_enrich`/`queue_counts`
  (одна вакансия под двумя профилями — две независимые строки, свой дедуп/схлопывание).
- `events`: `log_event` пишет строку; агрегация `{turn(since), total}` по видам корректна.
- `summary --since`: печатает валидный JSON ожидаемой формы и **не** импортирует torch
  (проверка лёгкости старта / отсутствия импорта).

Rust:

- Новое правило хода — чистая функция решения (apply-target достигнут / пул исчерпан И
  чат-часть закрыта по одному из условий) → `Switch(next)`/`Stop`, как нынешние
  `decide_apply_chain`/`next_eligible_in_order`.
- Разбор JSON `summary` из stdout (serde) с дефолтами для отсутствующих полей.

## Инцидент 2026-07-24: фулстак откликался на аналитика

Симптом: профиль fullstack слал отклики на «Системный аналитик», Backend Go/Python,
Security Engineer и прочие чужие роли.

Причины (три, наложились):

1. **Загрязнённый пул эпохи общего скана.** До перехода на пер-профильные поиски
   (коммит `3b7bde1`, 2026-07-24 16:52) скан ходил по union всех групп базового
   `config.yaml` и складывал всё под `profile='fullstack'` — в пуле фулстака скопилось
   2033 «Системных аналитика» плюс сотни Backend-вакансий (found_at 17–24 июля).
2. **Нет порога релевантности.** `MIN_SIMILARITY` в `.env` не был задан (дефолт 0.0).
   Ранжирование честно ставило чужое вниз, но по мере выедания пула «топ» сползал:
   в логах 24.07 score лучшего кандидата за вечер упал 0.688 → 0.646 («Системный
   аналитик в банк») → 0.636 — бот дошёл до мусора и продолжал откликаться.
3. **Мёртвый allow-list групп.** `ListingHunter` принимал `groups`, но
   `_rank_candidates` его не использовал — фильтра по группам профиля не было вовсе.

Починка:

- пер-профильные поиски/пул/enrich — уже в `3b7bde1` (реализация этой спеки);
- загрязнённая БД удалена (бэкап `data/autopilot.db.bak-20260724-222203`), пул
  каждого профиля наполняется заново его собственным сканом;
- ранжирование фильтрует пул по группам профиля (см. «Конфиг» выше; тест
  `tests/test_rank_group_filter.py`);
- в `.env` задан `MIN_SIMILARITY=0.60` — страховка от хвоста выеденного пула; чужие
  роли режет фильтр групп, а не порог (полосы score пересекаются: свои 0.64–0.75,

Урок: эмбеддинг-косинус на multilingual-MiniLM не отделяет «Системный аналитик в
банк» (0.646) от «Fullstack-разработчик» (0.678) — релевантность держится на

## Инцидент 2026-07-24 (вечер): сгоревший пул и зависший ход

Симптом: «бот откликался, но откликов нет», ход замер на fullstack, в следующий
профиль цикл не пошёл.

Причины:

1. **hh перестал показывать кнопку отправки** (`[data-qa='vacancy-response-submit-popup']`
   не появлялась; письмо заполнялось, submit — таймаут 5с). Каждый отклик падал в
   generic-ветку и помечался `failed`: за 23:15–23:46 сгорело 55 кандидатов — весь
   срез пула выше порога 0.60 (распределение свежего пула: медиана 0.50, ≥0.60 — 64
   из 304). UI показывал «0 откликов» честно — успешных не было.
2. **Предохранителя от серии сбоев не было**: 55 одинаковых инфраструктурных ошибок
   подряд не останавливали проход.
3. **«Пул пуст» не завершал фазу**: `run --apply` крутился вечно («Нет подходящих…»
   каждые 900с), а ротация хода в виджете срабатывает только на 27 успешных откликов
   или дневной лимит; сигналы `apply_idle`/`applies_exhausted` в `main.rs` объявлены,
   но никогда не выставляются — ход замер.

Починка:

- `SubmitNotFound` (site/base): таймаут кнопки отправки — НЕ вина вакансии; не
  записываем, остаётся в пуле. В лог — дамп data-qa видимых кнопок страницы
  (`_dump_buttons`) для починки селектора по факту.
- Предохранитель `_FAIL_STREAK_LIMIT = 3` (tasks/listings): столько подряд
  SubmitNotFound/неожиданных ошибок → прекратить проход (системная поломка, не
  вакансии). Успех и «нормальные» исходы (вопросы/отказ/снята) сбрасывают серию.
- `apply_from_queue` возвращает `None` при пустом пуле (0 — только дневной лимит);
  `run_forever(apply)` на `None` завершает процесс → виджет видит окончание
  apply-фазы и ведёт ход дальше (чат → ротация) существующей веткой.
- 55 сгоревших записей `failed` удалены из `applications` — вакансии вернулись в пул.
- Тесты: `tests/test_apply_fail_streak.py` (пул не горит, серия останавливает проход,
  успех сбрасывает серию, None/0 различаются).

Развязка (25.07, по дампу кнопок): разметка hh НЕ менялась. Кнопки отправки не было,
потому что страницы были в состоянии «уже откликались»: после удаления БД история
откликов стёрлась, свежий скан заново набрал те же вакансии, и топ по релевантности —
ровно те, куда бот уже откликался (у части — уже «Вас пригласили»/«Вам отказали»).
Детект `_already_responded` знал только «вы откликнулись» и плашки ответа работодателя
пропускал. Паттерн вынесен в `RESPONDED_PATTERN` и расширен («вас пригласили»,
«вам отказали») — такие вакансии помечаются `already` и уходят из пула; повторную
отправку страховал SubmitNotFound (письмо готовилось, но не уходило). Тест:
`tests/test_responded_pattern.py`. Урок: удаление БД стирает дедуп откликов — страничный
детект обязан покрывать все состояния плашки отклика.

Дожато следом (25.07), чтобы «уже откликались» не тратило ресурсы:

- **Письмо после проверки страницы.** Отклик разбит на `open_response` (открыть форму,
  все отказные состояния — уже откликались/пригласили/лимит/вопросы — вылетают здесь)
  и `submit_response` (заполнить и отправить). LLM-письмо генерируется между ними —
  повторные вакансии больше не жгут вызов LLM. Протокол адаптера обновлён
  (`SiteAdapter.open_response`/`submit_response`), тест
  `tests/test_letter_after_open_check.py`.
- **Детект на этапе обогащения.** Страница вакансии и так открыта — если на ней
  маркеры «вы откликнулись»/«вас пригласили»/«смотреть отклик» (`RESPONDED_MARKERS`,
  без ложного срабатывания на счётчик «уже откликнулись N человек»), fetcher кидает
  `VacancyAlreadyResponded`, обогащение помечает вакансию `already` — она уходит из
  пула до фазы откликов. Тест `tests/test_enrich_detects_responded.py`.
- **Гонка детекта с рендером hh.** Плашка «уже откликались» рисуется клиентским JS
  позже domcontentloaded: одиночная проверка через 600мс её пропускала — бот заполнял
  письмо, hh сохранял его как черновик формы (наблюдалось как «открыл вакансию — а
  письмо уже вписано»). Теперь `_wait_already_or_form` опрашивает до ~5с: плашка →
  AlreadyApplied, признак формы (submit/поле письма/вопросы) → продолжаем. Тест
  `tests/test_open_response_waits_banner.py`.
- **Модалка «вакансия в другой стране» и ложные already (найдено по вакансии
  135048005).** hh при таком предупреждении редиректит с формы отклика на страницу
  вакансии с модалкой `relocation-warning-confirm` («Все равно откликнуться»). Две
  беды: (1) подтверждение модалки жило в `submit_response`, до которого
  `_wait_already_or_form` не доводил — вакансии «в другой стране» молча
  пропускались; (2) на странице вакансии есть счётчик «уже откликнулись N человек»,
  и альтернатива `уже отклик` в `RESPONDED_PATTERN` матчилась на него — 40 вакансий
  за 5 минут получили ложный `already` (сняты из БД). Починка: паттерн сужен до
  форм с «вы/вас/ваш» (негативный тест на счётчик), модалка подтверждается прямо в
  цикле ожидания `_wait_already_or_form`, после чего ждём форму дальше. Тесты:
  `test_responded_pattern.py`, `test_open_response_waits_banner.py`
  (`test_relocation_warning_confirmed_and_form_opens`).
- **Быстрый отбой вместо полуминуты на «плохой» странице.** Отклик-состоявшийся
  детектится двумя маркерами: текстовая плашка (`_page_says_responded`) и DOM-кнопка
  чата по отклику `[data-qa='open-vacancy-chat']` — она надёжнее текста и ловит
  неизвестные формулировки; срабатывает на первом же опросе (~1с вместо цепочки
  5с плашка + 20с LLM + 10с поле + 5с кнопка). Если за 5с не появились ни плашка,
  ни форма — страница в неизвестном состоянии: мягкий пропуск SubmitNotFound без
  LLM и заполнения (вакансия в пуле, серия подряд прекращает проход).
