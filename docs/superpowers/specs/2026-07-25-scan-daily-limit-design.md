# Суточный лимит скана вакансий (пер-профиль)

Дата: 2026-07-25
Репозиторий правок: `~/projects/work-autopilot` (спека — в health-widget по конвенции)

## Проблема

Поиск новых вакансий (`autopilot run --scan`) в цикле запускается чаще одного
раза в сутки на профиль. Причина — как виджет определяет «профиль уже сканился
сегодня».

Гейт живёт в виджете (`health-widget/src/main.rs::begin_turn`):

```
scanned_today = summary.last_scan_date == today_local()
```

`last_scan_date` приходит из summary work-autopilot и считается так
(`store.py`):

```
SELECT date(MAX(found_at)) FROM queue WHERE profile = ?
```

`found_at` пишется только при вставке новой строки в `queue`. Если скан ничего
нового не нашёл (все вакансии — дубли, `enqueue` вернул `False`), `MAX(found_at)`
остаётся вчерашним. Тогда `last_scan_date != today`, и на следующей ротации
профиля или рестарте виджета `begin_turn` снова уходит в скан. Скан без находок
никогда не «засчитывается» → профиль сканит по кругу.

Охват лимита — пер-профиль: каждый профиль сканит максимум раз в сутки;
за день суммарно по одному скану на профиль. Это ожидаемое поведение, его и
чиним.

## Решение

Источник правды — в work-autopilot. Скан штампует дату запуска для профиля по
факту прохода группы, независимо от находок. `last_scan_date` читает этот штамп.

Виджет (`begin_turn`, гейт `scanned_today`) и формат summary/JSON
(`last_scan_date`) не меняются — начинают работать корректно на честном значении.

### 1. Журнал сканов в Store

Новая таблица:

```
scan_runs(
    profile  TEXT NOT NULL,
    ran_on   TEXT NOT NULL          -- локальная дата YYYY-MM-DD
)
```

Метод `Store.mark_scan_run(profile)`:

- пишет запись с `date('now','localtime')`;
- идемпотентен по дате: если за сегодня для профиля запись уже есть — не
  дублирует (проверка `SELECT 1 ... WHERE profile=? AND ran_on=date('now','localtime')`
  перед вставкой, либо `INSERT ... WHERE NOT EXISTS`).

### 2. Штамп в run_scan

`orchestrator.py::run_scan` вызывает `store.mark_scan_run(settings.profile_name)`
после каждого успешно завершённого `scan_group(group)` — в тон существующему
обновлению `scan.json` после каждой группы. `settings.profile_name` — тот же
ключ, под которым `scan_group` пишет строки в `queue` (`profile=settings.profile_name`
в `_build`), поэтому штамп и гейт по профилю совпадают. `store` уже собран в
`run_scan` через `_build`.

Семантика «по завершении группы»:

- скан с нулём новых, но дошедший до конца группы, — засчитывается (закрывает
  дыру);
- скан, прерванный (SIGTERM / рестарт) до конца первой группы, — не
  засчитывается и повторится (желательно).

### 3. last_scan_date читает журнал

`Store.last_scan_date(profile)`:

```
SELECT MAX(ran_on) FROM scan_runs WHERE profile = ?
```

С фолбэком на старую формулу по `queue`, если журнал пуст (обратная
совместимость: уже накопленные профили без записей в `scan_runs` на первом
запуске отдают дату по `MAX(found_at)`, как раньше).

## Ручные кнопки скана

`🔎 Все группы` и скан по группе в виджете дёргают тот же `--scan`, поэтому
штамп даты — побочный эффект самого скана. Виджет ручные кнопки не блокирует
(они идут мимо `begin_turn`), но после ручного скана дата за сегодня
проставится, и авто-цикл в этот день профиль уже не пересканит. Отдельная
логика не нужна.

## Что не трогаем

- health-widget: `begin_turn`, гейт `scanned_today`, сериализация state.
- Формат summary JSON и поле `last_scan_date`.
- Пер-профильность очереди `queue`.

## Тесты (work-autopilot, unit на Store)

1. `mark_scan_run(p)` → `last_scan_date(p)` == сегодня даже при пустой `queue`.
2. Фолбэк: `scan_runs` пуст, в `queue` есть строки → `last_scan_date` = дата по
   `MAX(found_at)` (старое поведение).
3. Идемпотентность: два `mark_scan_run(p)` в один день → одна запись за дату,
   `last_scan_date` = сегодня.

## Обновление 2026-07-26: 4 скана в сутки, гэп 6 часов

Правило «один скан в сутки на профиль» заменено на «до 4 сканов в сутки, но не
чаще, чем раз в 6 часов». Изменения:

- `scan_runs` теперь строка на КАЖДЫЙ запуск: PK `(profile, ran_on)` снят,
  добавлена колонка `ran_at` (локальный datetime). Миграция переносит старые
  дни как `ran_on || ' 00:00:00'`.
- `Store.scans_today(profile)` — счётчик запусков за календарный день,
  `Store.scan_age_minutes(profile)` — минут с последнего скана (None — не было).
  Оба уходят в summary как `scans_today` и `scan_age_min`; `last_scan_date`
  оставлен для совместимости.
- Гейт в виджете: `may_scan(scans_today, scan_age_min)` —
  `scans_today < SCANS_PER_DAY(4) && scan_age_min >= SCAN_GAP_MIN(360)`.
  В панели автопилота видно «🔎 сканов сегодня N/4 · следующий через Xч».
- Ручные кнопки скана лимит по-прежнему не спрашивают, но пишут штамп — и
  сдвигают ближайший авто-скан на 6 часов вперёд.
